# Ревизия проекта и план рефакторинга

Документ составлен по результатам статического разбора репозитория
(Karkasson, Vue 3 + Node.js/Socket.IO монорепо на pnpm workspaces).
Разделы 1–10 описывают состояние на момент ревизии и постепенно устаревают;
раздел 11 с отметками прогресса — рабочий.

Легенда приоритетов:

- **P0** — ломает продукт или безопасность, чинится малым диффом.
- **P1** — ломает инварианты, из-за которых система уже сейчас неверна.
- **P2** — узкое место по производительности или структуре.
- **P3** — гигиена, покрытие, документация.

### Чего не хватает

- **Пункт 1.10 откачен и требует переосмысления.** Очевидное лечение
  (`skipFollower()`, если симуляция предложила место, которого нет в живом
  состоянии) **ломает полную партию**: в `scoring.test.ts` вместо полного
  тайла на доску ложится 69–71 вместо 72, и падение оказалось
  нестабильным (зависело от раздачи). Исходный код на том же коммите проходит
  5 прогонов подряд. Инструментальный зонд показал, что спорная ветка на
  практике **не срабатывает ни разу** за полную партию, поэтому причина
  расхождения осталась непонятной. Изменение не зафиксировано: сначала нужно
  понять, что именно теряет один тайл, и только потом лечить. Лимит перебора
  тайлов (`AUTO_PLACE_TILE_ATTEMPTS`) откачен по той же причине.
- Пункт **1.5** (порядок «сохранить → разослать» при дисконнекте) исправлен
  **без отдельного регрессионного теста**: проверяется косвенно тестами
  переподключения. Стоит закрыть в фазе 7.
- Разделы 2.4 (900 плиток × 2 deep-watchers) и 4.2 (шторм клонов в ИИ) — самые
  дорогие по последствиям и ещё не начаты.

## 1. Сводка

Проект в целом читаемый и хорошо типизированный: в `server/src` нет ни одного
`any` и ни одного non-null assertion. Домен разделён на `GameManager` + четыре
менеджера + чистые `scoring`/`geometry`, тесты серверных правил сильные
(44 unit + 22 integration файла, две полные партии).

Проблемы сосредоточены в четырёх зонах:

1. **Целостность состояния.** Состояние меняется раньше, чем подтверждается
   сохранение; откат есть не везде; сериализации команд нет. Три из четырёх
   инвариантов из `server/AGENTS.md` сейчас нарушаются в продовом коде.
2. **Производительность.** Клиент рендерит 900 плиток с двумя deep-watchers
   каждая; ИИ делает тысячи глубоких клонов на один ход; стоимость команды
   растёт линейно с длиной партии.
3. **Границы слоёв.** Правила игры дублируются на клиенте в четырёх местах,
   `computerPlayer` эмитит Socket.IO-события, `Database.ts` создаёт хранилище
   на уровне модуля.
4. **Инфраструктура и агентские описания.** Type-aware линтинга нет — поэтому
   целый класс багов (необработанные промисы) невидим. Описания проекта
   существуют в пяти местах и уже начали расходиться.

## 2. P0 — Блокирующие дефекты

### 2.1 Активные партии удаляются через 30 минут

Цепочка:

- `GameService.saveGame` снимает **клон** партии — `GameService.ts:146-148`.
- `Database` проставляет `lastUpdate = Date.now()` на **клоне** —
  `Database.ts:31,69`.
- Живой объект игры хранит `lastUpdate = 0` от инициализации —
  `GameManager.ts:185`.
- `deleteStaleGames` читает `lastUpdate` у **живого** объекта и, если он
  нулевой, один раз проставляет `Date.now()` — `GameService.ts:451-457`.
- Дальше метка заморожена навсегда.

Итог: любую партию, начатую и не завершённую, снесут через 30 минут после
первого прохода сборщика, даже если в неё активно играют. Сборщик работает
каждые 10 секунд (`index.ts:16-33`, `config.ts:41`).

### 2.2 Нет отката при ошибке бизнес-логики

`saveGameOrRollback` (`handlers/game.ts:54-66`) откатывает только ошибку
сохранения. Ошибки домена в `catch` не откатываются:

| Хендлер          | `catch`       | Откат                          |
| ---------------- | ------------- | ------------------------------ |
| `PlaceTile`      | `game.ts:242` | нет                            |
| `PlaceFollower`  | `game.ts:333` | нет                            |
| `RecallAbbot`    | `game.ts:363` | нет                            |
| `MoveDragon`     | `game.ts:404` | есть (`copyStateFrom`, `:405`) |
| `ChoosePrincess` | `game.ts:445` | есть (`copyStateFrom`, `:446`) |
| `SkipFollower`   | `game.ts:476` | нет                            |

Последствия:

- **`PlaceTile`**: `setCurrentTileRotation` (`game.ts:115`, вызов `:215`) уже
  изменил `game.currentTile` до того, как `placeTile` может отказать
  (`game.ts:219-235`). При отказе поворот остаётся применённым и расходится с
  `tilesList`, из которого тайл будет перерисован.
- **`PlaceFollower`**: `FollowerManager.placeFollower` при неудаче сам вызывает
  `skipFollower() → endTurn()` (`FollowerManager.ts:229-231`). Ход уже потрачен,
  очередь в памяти сдвинута; затем хендлер бросает ошибку (`game.ts:326`),
  ловит её **без отката и без сохранения**. После реконнекта состояние
  разъезжается.

### 2.3 `skipFollower` не проверяет фазу хода

`handlers/game.ts:454-483` проверяет только очередь и отсутствие
`princessChoice`/`dragonMove`. Игрок может пропустить ход с выложенным тайлом и
передать очередь сопернику, минуя фазу выставления фишек.

### 2.4 Победитель считается по индексу, а не по id

```ts
// src/components/GameStats.vue:113
Object.values(props.gameBoard.scores).forEach((score, index) => {
  const player = props.gameBoard.players[index]
```

`scores` — `Record<PlayerId, number>`. Порядок ключей совпадает с массивом
только пока у каждого игрока есть запись. Игрок без очков (0) сдвигает
соответствие → в шапке и в карточке лобби показывается неверное имя и цвет.
То же в `GameLobby/GameCard.vue:53-70`, где дополнительно
`game.players[index].socketId` читается без `?.`. Ничьи не обработаны: победитель
всегда один, при нулевых очках возвращается `{ name: '', score: 0 }`.

### 2.5 Транзиентная ошибка Firebase уничтожает живую партию

`computerPlayer.ts:164-169,219-229`: любая ошибка в `service.saveGame(gameId)`
попадает в `catch`, который вызывает `deleteComputerGame(..., 'move failed')`.

## 3. P1 — Нарушенные инварианты

### 3.1 Нет сериализации команд

Все шесть мутирующих хендлеров выполняют `game.clone()` → мутация →
`await service.saveGame()` → `emit`. Между мутацией и `await` управление
отдаётся циклу событий, и вторая команда входит в свой хендлер.

- `copyStateFrom` (`GameManager.ts:993-995`, `Object.assign(this, deepClone(...))`)
  затирает изменение конкурирующей команды без проверки версии.
- `saveGame` ставит снимки в очередь (`GameService.ts:150-157`); побеждает
  порядок постановки в очередь, а не порядок логических изменений.
- Секрет-мьютекс на игру отсутствует.

### 3.2 Снапшот читается до `await`, публикуется после

`computerPlayer.ts:204` получает `updatedGame`, `:229` сохраняет, `:230`
разосылает. Если между 204 и 229 объект партии был заменён
(`GameService.startGame:299` перезаписывает `this.games[gameId]`), игроки
получат не то состояние, что в базе. То же в `connection.ts:37-43`: `void
service.saveGame(gameId)` выполняется **до** `ackGameUpdated` (`:43`),
публикуя незафиксированное состояние — прямое нарушение `server/AGENTS.md`.

### 3.3 Две команды вообще не сохраняются

- `game.ts:139-143` `SelectPlacingPoint` — мутирует `game.placingPoint`.
- `game.ts:170-175` `UpdateCurrentTile` — мутирует поворот `game.currentTile`.

Оба нарушают инвариант «сохранить перед ack»: состояние теряется при рестарте.

### 3.4 `deleteGame` может воскресить удалённую партию

`GameService.ts:135-141`: `await pendingSave` (`:137`) → `await db.deleteGame`
(`:138`). Если после `await` кто-то поставит новый `saveGame` в `pendingSaves`,
он выполнится **после** удаления и заново создаст запись.
`deleteStaleGames` (`:456`) вызывается параллельно с активными хендлерами.

### 3.5 Бесконечный цикл ходов бота

`GameManager.ts:743-753`: если симуляция предложила место, которого нет в живом
состоянии, не выполняется **ничего** — ни `placeFollower`, ни `skipFollower`.
Ход не завершается, `isPlacingFollower` остаётся `true`. Проверка «бот что-то
сделала» (`computerPlayer.ts:211-217`) считает только плитки и проходит, после
чего `runComputerMoves` (`:171-181`) снова планирует ход. Получается
бесконечная цепочка таймеров по секунде на одну партию.

Соседняя проблема: `autoPlaceTile` при отсутствии ходов делает рекурсивный
`await this.autoPlaceTile()` (`GameManager.ts:754-760`) без ограничителя
итераций; каждый уровень заново строит симулятор и перебирает доску.

### 3.6 Разрыв между клиентом и хранилищем

`connection.ts:25`: `const [game] = service.findPlayerGamesForSocket(socket.id)`.
Игрок, состоящий в двух лобби, обрабатывается при дисконнекте только в одном;
в остальных `socketId` остаётся навсегда, `isComputerPlayer` вернёт `false`,
таймеры ИИ для этой партии встанут.

### 3.7 Ошибки подтверждаются игроку техническим текстом

Каталог `GameErrors` обходится строковыми литералами минимум в девяти местах:
`game.ts:205,209,390,430`, `lobby.ts:56,63,70,77,252`. Клиент показывает
`error.message` пользователю (`src/utils/common.ts:7`), поэтому в русском
интерфейсе всплывают английские строки и внутренние сообщения сериализации.
`tests/unit/errors.test.ts:45-58` проверяет только одно направление — что
сообщения из каталога не дублируются в исходниках, но не что все сообщения
берутся из каталога.

### 3.8 Исключения из жизненного цикла партии

`GameManager.placeStartTile` бросает (`GameManager.ts:322,338`) внутри
`startGame`, который вызывается из конструктора (`:248`). Обработчики
`StartGame` (`lobby.ts:250` — вызов вне `try`) и `restoreComputerGames` не имеют
единого `catch`, поэтому исключение превращается в необработанный промис.

Отдельно: `createGameDatabase()` выполняется на уровне модуля
(`Database.ts:132`), поэтому отсутствие `FIREBASE_API_KEY` роняет процесс в
момент импорта, до `server.listen`, с невнятным стектрейсом
(`config.ts:72-78`, `Database.ts:127-129`).

### 3.9 Необработанные промисы на клиенте

`GamePlacingFollowers.vue:49,200`, `GameAbbotRecall.vue:91`,
`GameLobby.vue:49` — `emitAck` отклоняется по таймауту или ошибке, игрок ничего
не видит и считает, что ход прошёл. В `App.vue:350,515` и
`GamePrincessAndDragon.vue:67` то же сделано правильно — поведение
непоследовательно.

Дополнительно `emitAck` не снимается при обрыве: таймаут 15 с
(`GameService.ts:97-99`), обработчиков `disconnect`/`connect_error` нет. Для
`placeTile` это значит, что `App.vue:531` может уйти в `catch` уже после
восстановления соединения и показать ошибку при фактически применённом ходе.

### 3.10 Потеря слушателей при переподключении

`GameService.connect()` (`GameService.ts:118-138`) создаёт **новый** сокет,
только если `socket.connected` ложно. Слушатели, зарегистрированные
`onGameUpdated` (`:252-256`), захватывают `this.socket` в момент вызова, поэтому
после реконнекта все 8 слушателей остаются на мёртвом сокете, а
`App.vue:670-686` снимает их именно с него. Старый сокет не `disconnect()`-ится
и продолжает переподключаться.

## 4. P2 — Производительность

### 4.1 900 плиток × 2 deep-watchers = 1800 наблюдателей

`App.vue:283` дефолт `gridSize = [30, 30]` → `App.vue:129-173` рендерит 900
клеток. В каждой передаётся **один и тот же** массив `placedFollowers`
(`App.vue:157`) и массив `players` (`:158`). `TileView.vue:489-496` и
`:499-507` регистрируют два `watch(..., { deep: true })` — на `followers` и на
`tile`.

Каждый `gameUpdated` заменяет `gameState` целиком (`App.vue:400`) → все 1800
наблюдателей срабатывают, плюс `drawTile()` перерисовывает canvas во всех 900
клетках, хотя фишки изменились максимум в десяти.

### 4.2 Шторм глубоких клонов в ИИ

`GameSimulatorModule.findBestMove` (`:137-229`) для каждой позиции × поворота
делает `clone()` (`:104`), затем `cloneForSimulation()` (`:175`), затем **ещё
один** клон на каждое «место × тип фишки» (`:198`). `cloneForSimulation`
(`GameManager.ts:969-985`) сам вызывает `deepClone`. На доске в 60+ плиток это
тысячи полных клонов на один ход, синхронно внутри таймера.

### 4.3 Двойной клон на каждую команду

`handlers/game.ts:213` `game.clone()` → `GameService.ts:146-148` `game.clone()`
→ `serializeGameState` (`gameSave.ts:422` `JSON.stringify`). Обе операции
проходят по **неограниченно растущим** `actionsHistory` и `tileHistory`
(`GameManager.ts:346,794`), которые целиком уходят и в каждый `gameUpdated`
(`GameService.ts:494`), и в Firebase. Стоимость команды растёт линейно с
длиной партии, суммарно — квадратично.

### 4.4 Список игр десериализует всё хранилище

`getGamesList` (`GameService.ts:531-543`) вызывает `getAllGames`, который тянет
весь узел `games` и прогоняет `deserializeGameState` по каждой записи —
валидация плюс `migrateLegacyGameState`. Вызывается на каждый вход и обновление
любого клиента.

### 4.5 Прочее

- `GameObjectManager.getConnectedFeatureGroups:254-265` — вложенный
  `SIDE_NAMES.some(d => d === point.direction && directions.includes(d))`:
  сравнение по идентичности строк полностью избыточно, даёт O(n²).
- `GameTileManager.drawNextTile:150-176` — `for` × `findIndex` + `splice`,
  O(n²) по колоде, внутри перебор мест × 4 поворота.
- `deepClone` (`utils/common.ts:4-23`) — рекурсивный, без `structuredClone`, без
  защиты от циклов, теряет прототип. Это фундамент пунктов 4.2 и 4.3.
- `GameService.formatGameData:466-499` отдаёт живые ссылки на
  `actionsHistory`, `players`, `currentPlayer` без клонирования. Сегодня работает
  потому, что `shared.ts:15` сразу сериализует их в emit, но контракт не
  защищает: любой будущий потребитель (кэш, очередь, тест) получит изменяемый
  доменный объект.

## 10. Описания для агентов в разном виде

Агентские описания существуют в пяти местах и уже начали расходиться.

### 10.1 `AGENTS.md` — три файла

Структура «корень + слой» (`AGENTS.md`, `src/AGENTS.md`, `server/AGENTS.md`)
выбрана верно: корневой файл задаёт инварианты, дочерние добавляют детали слоя
и явно ссылаются на корень. Проблемы:

1. **Правила привязаны к конкретным файлам и строкам** — «`server/src/socket/handlers/`»,
   «`GameSimulatorModule.findBestMove`». Такие ссылки протухают, а правятся
   хуже, чем общее правило.
2. **Требования к покрытию не сформулированы как норма.** Есть указание «добавь
   или обнови проверки», но нет определения «какой слой какой минимум должен
   покрывать» — §8 показывает, что половина серверных менеджеров не покрыта
   вообще, и это формально не нарушение.
3. **Нет определения готовности PR**: ни чек-листа проверок, ни требования
   обновлять `AGENTS.md` при изменении архитектуры, ни указания, что делать с
   уже расходящимися утверждениями.
4. **Пересечение с `README.md`.** Таблица команд, дерево репозитория, описание

рассинхронизация состояния и неверное отображение победителя, и одновременно
добавлены инструменты, которыми проверяется всё остальное. Обе фазы закрыты
полностью, см. раздел 0.

**Что делать дальше.** Фаза 2 (конкурентность и транспорт) — следующая по
очереди. Она опирается на type-aware линтынг из фазы 0 и на стабильное
состояние партии из фазы 1, поэтому обе её части (мьютекс на игру и единый
преамбул хендлеров) впервые можно делать без риска, что регрессию не удастся
локализовать. Начинать с 2.1 и 2.2.

**Что можно отложить.** Фаза 6 (правила) не влияет на корректность игры, кроме
пункта 6.3 — расхождение чисел в тексте правил с реальным подсчётом стоит
исправить, но это не блокер. Фаза 8 — гигиена; её полезно сделать до того, как
`README` и `AGENTS.md` разойдутся ещё сильнее, но она не блокирует работу.

**Основные риски.**

- Фаза 4.7 (переписывание ИИ-симулятора) — самая рискованная: затрагивает
  поведение ботов, проверяется только двумя полными партиями. Проводить её
  отдельным этапом после того, как фаза 1 закроет нестабильность состояния,
  иначе регрессии будет невозможно локализовать.
- Фаза 7.1 (разбор зеркала в `gameplay.ts`) может временно ослабить проверку
  очков. Сначала зафиксировать текущие ожидания, потом переходить на
  независимый оракул.
- Фазы 1–3 меняют порядок «сохранить → опубликовать». Это правильное изменение,
  но оно делает временные сбои заметными: игроки начнут чаще получать явную
  ошибку вместо тихого рассинхрона. Это ожидаемо и нужно отразить в CHANGELOG
  как исправление надёжности.
- Включение type-aware линтинга (0.1) может дать большой объём новых
  предупреждений. Подавить их не подавляя, а прогнать списком задач.
  **Сработало:** 86 срабатываний, из них 17 в продуктовом коде и все — реальные
  дефекты.
