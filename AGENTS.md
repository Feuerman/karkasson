# Инструкции для агентов и контрибьюторов

Корневой `AGENTS.md` — единый источник общих инструкций. `src/AGENTS.md` и
`server/AGENTS.md` содержат только дополнения для соответствующих слоёв.
Обновляй эти инструкции вместе с `README.md`, если меняются архитектура,
источники истины или порядок работы.

Проект — онлайн-игра «Каркассон»: Vue 3 SPA в `src/`, сервер Node.js/Socket.IO
в `server/`, Firebase Realtime Database, pnpm workspace. Архитектура и запуск —
в [README.md](README.md), история изменений — в [CHANGELOG.md](CHANGELOG.md).

## Основные инварианты

- Игровое состояние, правила и очки принадлежат серверу. Клиент отображает
  серверное состояние и отправляет намерения; не переносить на него валидацию.
- Сервер заново разрешает игровые объекты из состояния партии и проверяет
  очередь и допустимость команды — не доверять присланным клиентом объектам.
- Единственная доменная модель — `server/src/modules/types.ts` (`@server/*`);
  типы Socket.IO-контракта — `src/types/socket.ts`.
- Команды клиента подтверждаются ack через `src/modules/GameService.ts`;
  широковещательные события только синхронизируют состояние.
- Каталог тайлов определён в `server/src/data/tileCatalog.ts`, клиентский файл
  его переэкспортирует. Сопоставлять стороны по именам; `rowIndex` — Y,
  `tileIndex` — X.
- Сохранения: формат — `server/src/modules/gameSave.ts`, перечень полей —
  `server/src/modules/gameState.ts`. Новые форматы должны сохранять миграции.
- Предпросмотр поворота тайла и выбор клетки живут только в памяти сервера:
  это временное состояние интерфейса, оно не сохраняется и сбрасывается при
  перезапуске сервера.
- Прикладные сообщения клиента и сервера проходят через scoped logger в
  `src/utils/logger.ts` и `server/src/utils/logger.ts`; прямой `console` в
  прикладном коде не используй. Для сервера уровень задаёт `LOG_LEVEL`.

## Работа над изменениями

- Делай минимальный связный diff и следуй локальным паттернам. Для анализа без
  запроса на реализацию не редактируй файлы; не перечитывай сведения, уже
  доступные в контексте. Исследуй только код и проверки, нужные задаче.
- Для неоднозначного изменения игрового поведения, протокола или сохранений
  сначала уточни решение; в остальных случаях выбирай наименее рискованный путь.
- Сопоставляй поведение с тестами и закрывай обнаруженные пробелы: типы и сборка
  не заменяют поведенческие проверки.
- Не запускай полный набор проверок часто или автоматически после каждой правки:
  это может раздувать контекст. По необходимости запускай локальные проверки,
  относящиеся к затронутой области, особенно при диагностике ошибок. Финальные
  проверки пользователь может выполнить самостоятельно. Стандартный набор
  финальных проверок запускается командой `pnpm run check:all`.
  В конце работы укажи этот набор; дополнительные проверки вне стандарта
  перечисляй отдельно, только если они нужны для изменения. Если пользователь
  отдельно просит проверить изменения или требуется локально разобраться с
  проблемой, запускай необходимые проверки. Не ослабляй проверку типов;
  серверная сборка должна проходить `tsc`.
- Новый TypeScript — без `any` и non-null assertion; зависимости не добавляй,
  пока не проверишь имеющиеся библиотеки. Неизвестные API сверяй с актуальной
  документацией.
- После каждого изменения `AGENTS.md` запускай `pnpm exec prettier --write AGENTS.md`.
- Отвечай по-русски и кратко: результат, затронутые области и фактически
  выполненные проверки. Отмечай, если проверки не запускались или поведение
  приложения не менялось.

## Команды и проверки

| Команда                          | Назначение                                  |
| -------------------------------- | ------------------------------------------- |
| `pnpm run type-check`            | проверка типов клиента (`vue-tsc --noEmit`) |
| `pnpm test`                      | полный набор Vitest: unit и integration     |
| `pnpm run test:coverage`         | тесты и пороги покрытия по слоям            |
| `pnpm run test:gameplay`         | две полные партии: 4 ИИ и человек против ИИ |
| `pnpm run test:browser`          | браузерный smoke: лобби, слоты, запуск игры |
| `pnpm run lint`                  | ESLint, только проверка                     |
| `pnpm run build`                 | проверка типов и production-сборка клиента  |
| `pnpm --filter server run build` | компиляция сервера (`tsc`)                  |
| `pnpm run check:all`             | форматирование и полный набор проверок      |

`pnpm run format` форматирует файлы; не запускай на всём репозитории ради
несвязанной правки.

### Проверки по областям

- Игровые правила/ходы: полный `pnpm test`, сборка сервера и проверка типов;
  `pnpm run test:gameplay` можно добавить как быструю регрессию, но не вместо
  полного набора.
- Интеграционные тесты запускают настоящий сервер и Vite. `pnpm run
test:browser` проверяет реальный UI и требует Chromium
  (`pnpm exec playwright install chromium`).
- Браузерные тесты подключают серверный код из сборки `server/dist` через
  `createRequire`: пакет сервера — CommonJS, а Playwright не умеет импортировать
  его исходники как ES-модуль с именованными экспортами. Обычный импорт вида
  `import { ... } from '@server/...'` в `tests/browser/` ломает запуск на Node 20.

- Изменения тестов и production-кода должны сохранять пороги `pnpm run
test:coverage`: строки/операторы/функции/ветви — не ниже 85/85/85/75% для
  серверных модулей, 80/80/85/70% для сервисов, 70/70/80/65% для Socket.IO и
  70/70/60/50% для клиентских модулей, композаблов, утилит и правил, имеющих
  автоматические unit-тесты. UI-компоненты проверяются отдельными браузерными
  сценариями. При росте покрытия поднимать пороги адресно; не снижать их без
  обоснования и обновления плана.

## Соглашения репозитория

- Prettier: без точек с запятой, одинарные кавычки, 2 пробела,
  `trailingComma: es5`, `printWidth: 80`; ESLint — `.eslintrc.json`.
- Алиасы: `@/*` → `src/*`, `@server/*` → `server/src/*`. Клиентский UI:
  Nuxt UI v4, Tailwind tokens; уведомления — через notification plugin.
- Сообщения коммитов — на русском, с принятым префиксом области (`Server`,
  `Client`, `Changelog:`); Conventional Commits не используются.
- Продуктовые изменения сопровождаются записью в CHANGELOG и SemVer-версией
  корневого `package.json` перед релизом; документация и tooling обычно не
  требуют релизной версии.
- CHANGELOG читают игроки и пользователи, поэтому его язык отличается от языка
  кода и инструкций:
  - изменения игровых правил, дополнений и подсчёта очков описываются подробно,
    с числами и примерами;
  - изменения интерфейса описываются подробно: что изменилось для игрока и как
    это влияет на удобство;
  - изменения сервера, сборки, хранилища и проверок описываются кратко и общими
    словами, без имён файлов, модулей, функций, типов, полей, переменных
    окружения, версий схем и внутренних механизмов. Публичная CHANGELOG не
    должна быть источником сведений о внутреннем устройстве и не должна
    раскрывать детали, полезные посторонним.
  - Не переноси внутренние детали из `AGENTS.md` в публичный CHANGELOG.
- Локальный `.env.local` игнорируется Git; не коммить секреты. Не добавляй
  ключи и токены в Firebase-конфигурацию.
- Общие настройки OpenCode (`.opencode/opencode.json` и команды) хранятся в Git;
  локальные пакеты плагинов, зависимости, lock-файлы и секреты остаются
  игнорируемыми.
