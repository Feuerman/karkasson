# Серверные инструкции для агентов

Дополнение к корневому `AGENTS.md`; здесь только правила серверного слоя.

## Границы ответственности

- `modules/GameManager.ts` — источник истины для состояния и правил игры.
- `socket/handlers/` — транспортный адаптер: проверяет форму команды,
  идентичность/права, вызывает доменную логику и формирует ack.
- `services/GameService.ts` — лобби, реестр, жизненный цикл и персистентность;
  не добавляй сюда Socket.IO-зависимость.
- `modules/Database.ts` — реализация `IGameDatabase`: хранит уже сериализованные
  строки и не знает формата сохранения; ошибки записи и чтения должны быть видны
  вызывающему коду, если операция обязательна для команды.
- `modules/gameState.ts` — перечень полей, которые переживают сохранение, и
  снятие снимка состояния.

## Инварианты безопасности и сохранения

- Никогда не доверяй присланным клиентом состояниям плитки, объекта, фишки,
  счёта или игрока. Клиент передаёт только намерение (например, координаты и
  поворот); цель и допустимость заново разрешаются из серверного состояния.
- Firebase Realtime Database: клиентам доступ закрыт правилами
  `database.rules.json`; сервер входит по custom token сервисного аккаунта из
  `FIREBASE_SERVICE_ACCOUNT`. Не возвращай клиентский Firebase SDK и не
  ослабляй правила ради локальной отладки.
- Каждый изменяющий игровой запрос проверяет существование партии, очередь,
  фазу хода и допустимые значения до изменения состояния.
- Перед подтверждением изменяющего запроса сохраняй новое состояние. При
  ошибке сохранения откатывай изменение и возвращай ack с `error`; не
  публикуй незафиксированное состояние. Исключение — транзиентные команды:
  предпросмотр поворота тайла и выбор клетки меняют состояние только в
  памяти и не сохраняются, потому что на правила они не влияют. Это правило
  действует и для выхода из начатой партии (`LeaveGame`).
- Удаление партии идемпотентно: при ошибке хранилища возвращай состояние в
  память, иначе после перезапуска партия «воскреснет» из устаревшей записи.
  Повторные удаления одной партии должны объединяться.
- Таймауты и повторы Firebase живут в реализации `IGameDatabase`
  (`modules/databaseRetry.ts`), а не в `GameService`: тестовые хранилища
  должны сохранять управляемые сбои и задержки.
- Очередь сохранений одной партии ограничена; при переполнении возвращай
  `CommonErrors.SaveFailed`. Число операций, возраст старейшей и число
  ошибок отдавай через `GameService.storageStatus()`.
- Изменяющие игровые команды принимают необязательный `commandId`; успешный
  ключ (`команда:commandId`) помнится ограниченное время, а повтор возвращает
  текущее состояние без нового применения. Транзиентные команды не кэшируй.
- Транзиентная правка состоит из проверки и одного присваивания: частичного
  изменения не бывает, поэтому снимок состояния и откат ей не нужны.
- Любая команда лобби проверяет право вызывающего менять конкретный слот или
  запускать игру. `gameId` сам по себе не является авторизацией.
- Для таймеров ИИ держи не более одной цепочки на игру. Учитывай удаление и
  остановку партии; после `await` повторно проверяй, что игра ещё существует.
- Ход компьютера ограничен watchdog; зависшую партию удаляй и не возобновляй.
  После перезапуска не поднимай больше автоматических партий, чем глобальный
  предел, и не создавай партию без двух игроков с именем.
- У сессии один активный сокет: новая вкладка забирает управление и занятые
  слоты, старая получает `SessionReplaced`; второй слот той же сессии не
  создаётся.
- Сериализуемое состояние должно быть plain JSON; методы класса и временные
  runtime-объекты не сохраняются. Состав полей задаёт
  `SERIALIZED_GAME_FIELDS`: новое поле состояния добавляй туда явно, иначе оно
  не переживёт сохранение.
- Envelope схемы и преобразования данных находятся в `modules/gameSave.ts`.
  Для новой схемы увеличивай `GAME_SAVE_SCHEMA_VERSION`, добавляй миграцию
  предыдущей версии и покрывай сериализацию и восстановление тестами.
- Нормализация состояния (правила, сады, пулы подданных, список лидеров)
  выполняется только в `deserializeGameState`. Не дублируй её при загрузке:
  расхождение двух дефолтов уже стоило игроку фишки.
- Нечитаемое сохранение нельзя терять молча: считай его и отдавай число в
  `GameService.storageStatus()`.
- Список лобби читается из сводок `gameSummaries`, а состояние и сводка
  пишутся одной операцией. Не возвращай чтение всего узла игр ради списка.
- При старте поднимай только незавершённые партии; завершённые загружай по
  требованию. Активную партию без подключённых игроков удаляй только по сроку
  заброшенности, а завершённые — по сроку хранения.

## Проверки серверного слоя

- Для правил и ходов обязательны полный `pnpm test` и
  `pnpm --filter server run build`.
- Для протокола: добавь интеграционный тест через настоящий `TestClient` и
  тестовый `createGameServer`; обнови клиентский контракт в `src/`.
- При изменении сохранений проверь round-trip/перезапуск в
  `tests/integration/persistence.test.ts`.
- Не используй `void` для обязательного сохранения/удаления. Фоновая задача
  обязана иметь обработчик ошибок.
