# Поля: каталоговая топология и план реализации

Рабочий документ для следующих сессий. На текущем этапе описывается только
геометрия полей на тайлах; игровые правила, постановка крестьян и подсчёт очков
не меняются.

## Правила, согласованные для реализации

- Крестьянин ставится на доступную зелёную область выложенного тайла и остаётся
  на поле до конца партии.
- Большой подданный может быть крестьянином; при подсчёте он весит два обычных.
- Отдельное поле — связная зелёная область. Её ограничивают города, дороги,
  реки при соответствующем дополнении и край доски. Диагональ сама по себе
  соседством не является.
- В финальном подсчёте хозяин поля — игрок или игроки с максимальным взвешенным
  числом крестьян на нём. Каждый хозяин получает по 3 очка за каждый уникальный
  завершённый город, непосредственно граничащий с этим полем.
- Размер поля значения не имеет; незавершённые города не дают очков. Один и тот
  же завершённый город может дать по 3 очка нескольким независимым полям.

## Первый этап: каталог

Каждое определение в каталогах `server/src/data/tiles.ts` и
`server/src/data/*Tiles.ts` содержит явную топологию поля. Поле разбито на
локальные регионы; у региона указаны граничные полусегменты (например,
`eastNorth` — верхняя половина восточной стороны) и индексы групп городов,
соприкасающихся с регионом. Пустой список означает, что на тайле нет поля.
Общие типы и геометрические функции находятся в `fieldTopology.ts`, проверки
описаний — в `fieldTopologyValidation.ts`.

Для соединения соседних тайлов полусегмент сопоставляется с противоположным
полусегментом той же границы: `eastNorth` ↔ `westNorth`, `southWest` ↔
`northWest` и т. п. Поэтому поле может выходить к соседу через край, середина
которого занята дорогой/рекой, а четыре квадранта у перекрёстка остаются
раздельными. Например, у тайла L северо-западный и северо-восточный квадранты
связаны над перекрёстком, нижний левый и нижний правый — отдельные области.

Это справочные данные: они пока не копируются в состояние партии, не участвуют
в повороте тайла, обнаружении доступных мест или подсчёте очков. Каталог
ориентирован в исходное положение тайла; перед использованием в логике его
топологию нужно будет поворачивать тем же числом четвертей, что стороны и
`roadGroups`/`cityGroups`.

## Следующие шаги

✓ 1. (закрыто — проверено вручную) Продолжить визуальную сверку всех записей каталога с изображениями тайлов,
включая дополнительные наборы. Проверять не только число областей, но и
соответствие каждого указанного граничного порта непрерывной зелёной зоне;
проверить по официальным правилам, какие реки в каких наборах разделяют
поле. Каталог — явная ручная топология, цветовая автосегментация картинки не
является источником истины. 2. Для спорных тайлов проверять мини-примеры с соседними тайлами: поле должно
соединяться только через один и тот же геометрический полусегмент, включая
стороны, у которых середина занята дорогой/рекой. Не выводить соединения
только по `sides` или `roadGroups`. 3. Добавить поворот граничных портов поля; тестировать
повороты 0/90/180/270 и обратный поворот. Сопоставление противоположных
портов должно сохраняться при повороте. 4. Усилить проверки каталога: каждый порт назначен максимум одному региону,
ссылки на группы городов существуют, вся зелёная граница учтена; допускаются
внутренние области без выхода к краю, если их подтверждает рисунок/правило. 5. Реализовать серверное построение связных компонент поля по поставленным
тайлам. Соединять только соседние области через общую границу; учитывать
дороги и активные реки как разделители. Сначала допустимо пересчитывать
компоненты поиском от доски; не сохранять производный индекс, пока
производительность не покажет необходимость. 6. Привязать точку постановки крестьянина к локальному участку и компоненте
поля; не возвращать крестьян в запас. Сохранить проверку занятости поля
серверной. 7. Реализовать финальный подсчёт: по каждому полю собрать уникальные
соприкасающиеся завершённые города, посчитать крестьян (большой — за двух),
определить всех лидеров и начислить каждому по 3 очка за каждый такой город.
Один город должен учитываться отдельно на каждом поле, но только один раз
внутри одного поля. 8. Добавить unit- и integration-проверки разбиения/слияния полей, границ доски,
дорог, рек, нескольких групп города, ничьих, большого подданного,
незавершённого города и одного города у нескольких полей. Проверить
совместимость с флагом финального подсчёта и журналом очков. 9. Если состав поля или кэш компонент понадобится хранить в состоянии,
определить его как производное состояние либо добавить миграцию сохранений;
источник истины — выложенные тайлы и крестьяне, а не кэш.

## Технические ограничения

- Доменные решения остаются на сервере; клиент отправляет намерение поставить
  фишку, а не идентификатор поля или список городов.
- Не хранить у поля заранее поддерживаемый список городов без доказанной
  необходимости: город может сливаться с другим при каждом ходе. Для финала
  безопаснее собирать уникальные города по контактам поля.
- Река является границей поля только когда она присутствует в правилах партии.
- Изменение формата сохранения для текущего каталогового этапа не требуется.
