# Поля: каталоговая топология и план реализации

Рабочий документ по реализации полей. Серверная топология, постановка крестьян
и финальный подсчёт уже реализованы; ниже зафиксированы выполненные этапы и
оставшаяся работа над клиентским интерфейсом и сквозными проверками.

## Правила, согласованные для реализации

- Крестьянин ставится на доступную зелёную область выложенного тайла и остаётся
  на поле до конца партии.
- Большой подданный может быть крестьянином; при подсчёте он весит два обычных.
- Отдельное поле — связная зелёная область. Её ограничивают города, дороги,
  реки при соответствующем дополнении и край доски. Диагональ сама по себе
  соседством не является.
- В финальном подсчёте хозяин поля — игрок или игроки с максимальным взвешенным
  числом крестьян на нём. Каждый хозяин получает по 3 очка за каждый уникальный
  завершённый город, непосредственно граничащий с этим полем.
- Размер поля значения не имеет; незавершённые города не дают очков. Один и тот
  же завершённый город может дать по 3 очка нескольким независимым полям.

## Первый этап: каталог

Каждое определение в каталогах `server/src/data/tiles.ts` и
`server/src/data/*Tiles.ts` содержит явную топологию поля. Поле разбито на
локальные регионы; у региона указаны граничные полусегменты (например,
`eastNorth` — верхняя половина восточной стороны) и индексы групп городов,
соприкасающихся с регионом. Пустой список означает, что на тайле нет поля.
Общие типы и геометрические функции находятся в `fieldTopology.ts`, проверки
описаний — в `fieldTopologyValidation.ts`.

Для соединения соседних тайлов полусегмент сопоставляется с противоположным
полусегментом той же границы: `eastNorth` ↔ `westNorth`, `southWest` ↔
`northWest` и т. п. Поэтому поле может выходить к соседу через край, середина
которого занята дорогой/рекой, а четыре квадранта у перекрёстка остаются
раздельными. Например, у тайла L северо-западный и северо-восточный квадранты
связаны над перекрёстком, нижний левый и нижний правый — отдельные области.

Каталог ориентирован в исходное положение тайла. При размещении топология
поворачивается вместе со сторонами и `roadGroups`/`cityGroups`; по ней сервер
находит доступные места крестьян и строит связные компоненты полей. Список
поставленных крестьян сохраняется в состоянии партии, а компоненты каждый раз
вычисляются по выложенным тайлам и не сохраняются как отдельный индекс.

## Следующие шаги

✓ 1. Визуально сверить вручную записи каталога со всеми изображениями тайлов,
включая дополнительные наборы; проверено соответствие областей, граничных
портов и правил разделения полей реками. Источник истины — ручная топология и
правила игры, а не цветовая автосегментация.
✓ 2. Проверить соединение соседних областей по одинаковому геометрическому
полусегменту, в том числе у дорог и перекрёстков. Покрыто тестами построения
компонент в `tests/unit/fieldComponents.test.ts`.
✓ 3. Реализовать поворот граничных портов поля на 0/90/180/270 градусов и
обратный поворот; сопоставление портов сохраняется. Реализация и проверки —
`server/src/modules/tileRotation.ts`, `tests/unit/tileRotation.test.ts`.
~ 4. Базовые проверки каталога реализованы: регион имеет порты, порт не
повторяется в нескольких регионах, ссылки на группы городов существуют. Все
определения каталога проверяются в `tests/unit/tileCatalog.test.ts`; визуальная
сверка выполнена вручную. Остаётся решить, нужно ли усилить автоматическую
проверку полноты зелёной границы: обычная проверка каталога сейчас не выявляет
неописанный граничный порт. Дополнительное сравнение с сегментацией запускается
при наличии `SEG_OUT`.
✓ 5. Реализовать серверное построение связных компонент по соседним областям
выложенных тайлов. Соединение определяется совпадающими полусегментами, поэтому
дороги и активные реки остаются разделителями. Компоненты пересчитываются по
доске и не хранятся отдельным индексом. Реализация —
`server/src/modules/fieldComponents.ts`; базовые сценарии покрыты в
`tests/unit/fieldComponents.test.ts`.
✓ 6. Привязать постановку крестьянина к локальному региону и компоненте поля;
не возвращать поставленного крестьянина в запас и проверять занятость поля на
сервере. Реализовано через сериализуемое состояние `fieldFollowers`,
`FollowerManager.findAvailableFieldPlaces`/`placeFieldFollower` и управление в
`GameManager`. Unit-тесты — `tests/unit/fieldFollowers.test.ts`.
✓ 7. Реализовать финальный подсчёт: собрать уникальные завершённые города,
соприкасающиеся с полем, взвесить больших крестьян за двух, определить всех
лидеров и начислить каждому по 3 очка за город. Город учитывается отдельно для
каждого поля и один раз внутри поля. Реализовано в `scoreFields` (`finalScoring.ts`),
запись идёт под `ObjectTypes.FIELD` с `isFinalScoring`; unit-тесты —
`tests/unit/fieldFollowers.test.ts`.
~ 8. Unit-проверки постановки и подсчёта покрывают занятость компонентов,
несколько групп города, ничьи, большого крестьянина, незавершённые города и
город у нескольких полей (`tests/unit/fieldFollowers.test.ts`); построение
компонент и разделение областей покрыты в `tests/unit/fieldComponents.test.ts`.
Остаются сквозной сценарий через сокет и браузерные проверки после клиентской
доработки (этап 14), а также адресные проверки не покрытых unit-тестами
граничных случаев.
✓ 9. Решение о хранении состояния: в сохранение входят поставленные крестьяне
(`fieldFollowers`); топология берётся из каталога, компоненты являются
производными от выложенных тайлов и отдельно не сохраняются. Дополнительный
кэш и миграция для индекса компонент не нужны.

## Следующий этап: клиент

Клиент уже использует общий поток постановки подданного (`PlaceFollower`) и ack
с обновлённым состоянием игры; подписи поля и крестьянина добавлены. Отдельного
клиентского отображения `fieldFollowers`, выбора региона поля и категории очков
«Поля» пока нет. Для полей нужно отображать серверные данные, не рассчитывая
допустимость постановки локально.

10. Проверить прохождение серверных `fieldFollowers` и точек с `regionIndex` через
    клиентское состояние и типы контракта; добавить клиентскую обработку там, где
    эти данные сейчас теряются. Использовать существующий ack
    `GameService.placeFollower` для обновления состояния — отдельный ack для
    крестьянина не нужен.
11. Доработать выбор места крестьянина: показывать доступные регионы поля,
    различать несколько регионов на одном тайле и отправлять точку с правильным
    `regionIndex`. Использовать список доступных мест от сервера; не объединять в
    одну кнопку разные регионы. Добавить понятный режим выбора и обработку ошибок
    ack. Отдельный hit-testing по рисунку тайла нужен только если кнопочного выбора
    недостаточно для однозначного выбора региона.
12. Отобразить поставленных крестьян на доске. Учесть, что серверное состояние
    `FieldFollower` отделено от обычного `PlacedFollower`; выбрать визуальную точку
    для каждого региона, не терять маркер при повороте тайла и различать обычного
    и большого крестьянина.
13. Показывать очки за поля отдельно в итогах и статистике вместо включения в
    «Прочее». В журнале финального подсчёта явно называть крестьянина и начисление
    за завершённые города, сохранив серверную детализацию как источник данных.
14. Добавить сквозные проверки: постановка крестьянина через сокет с успешным
    ack и ошибкой для недоступного/занятого региона; браузерный сценарий выбора
    региона и отображения фишки; отображение начисления за поле после финального
    подсчёта.

## Технические ограничения

- Доменные решения остаются на сервере; клиент отправляет намерение поставить
  фишку, а не идентификатор поля или список городов.
- Не хранить у поля заранее поддерживаемый список городов без доказанной
  необходимости: город может сливаться с другим при каждом ходе. Для финала
  безопаснее собирать уникальные города по контактам поля.
- Река является границей поля только когда она присутствует в правилах партии.
- Изменение формата сохранения для текущего каталогового этапа не требуется.
