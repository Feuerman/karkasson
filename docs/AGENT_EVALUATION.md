# Оценка AI-агентов на проекте

Статус: методология, задач ещё не прогонялось
Область: сравнение моделей/агентов на любых будущих задачах проекта
Назначение: проверить гипотезу «модель B справляется не хуже модели A» на
реальных задачах, а не на ощущениях и публичных бенчмарках.

Документ не содержит выводов о конкретных моделях. Он задаёт воспроизводимый
протокол: какие задачи брать, как проводить прогон, что измерять, как решать,
менять ли рабочий инструмент.

## 1. Когда применять

- Появился новый кандидат: модель, версия, набор правил, другой агент.
- Хочется понять, оправданы ли платные лимиты или более медленная модель.
- Есть подозрение, что «стало хуже/лучше», но нет доказательств.
- Не применять для оценки отдельной спорной правки: это инструмент сравнения
  инструментов, а не ревью кода.

## 2. Принципы

1. **Сравниваем результат, а не стиль ответа.** Ценность агента — принятый
   дифф, а не красивый текст.
2. **Слепая оценка.** Ревьюер не знает, какая модель сделала дифф.
3. **Одинаковые условия.** Один стартовый коммит, одна формулировка задачи,
   одинаковые права инструментов и бюджет.
4. **Несколько задач.** Одна задача ничего не доказывает; минимум 8–12.
5. **Считаем стоимость принятия.** Время ревью и переделок — часть цены.
6. **Фиксируем всё.** Промпты, диффы, логи проверок, время, лимиты.

## 3. Что сравниваем

Перед стартом зафиксируй карточку участников:

| Поле              | Пример                          |
| ----------------- | ------------------------------- |
| Модель / агент    | A: ..., B: ...                  |
| Версия и дата     | ...                             |
| Настройки         | reasoning, temperature, лимиты  |
| Доступ к инструм. | одинаковый                      |
| Режим             | plan/build, правила `AGENTS.md` |
| Лимит на задачу   | время или токены                |

Если условия различаются (например, у одной модели обрезан контекст или
жёсткий rate limit), это фиксируется как отдельный фактор, а не замалчивается.

## 4. Набор задач

Бери реальные задачи из `PRODUCTION_READINESS.md` или бэклога, не синтетику.
Стратифицируй по типам, чтобы одна сильная сторона модели не перевесила:

| Тип                    | Минимум |
| ---------------------- | ------- |
| Исправление бага       | 2       |
| Небольшая фича         | 2       |
| Рефакторинг            | 1       |
| Пробел в тестах        | 1       |
| Протокол / сохранения  | 1       |
| UI / клиент            | 1       |
| Tooling / документация | 1       |

Требования к задаче:

- [ ] Однозначная цель и критерий готовности.
- [ ] Проверяема штатными командами (`pnpm test`, `type-check`, `lint`,
      `build`, при необходимости `test:browser`).
- [ ] Не требует секретов и внешних сервисов.
- [ ] Решается в разумном бюджете (ориентир: до 30–60 минут агента).

Порядок задач и моделей рандомизируй, чтобы усталость и разогрев не влияли
на одну сторону.

## 5. Протокол прогона

1. **Изоляция.** На каждый прогон — отдельный `git worktree` или ветка от
   одного и того же коммита `BASE_SHA`. Рабочее дерево чистое.
2. **Промпт.** Одинаковый шаблон (раздел 9), без подсказок о решении.
   Запрет на коммит, пуш и правку чужих файлов вне задачи.
3. **Прогон.** Одна свежая сессия на задачу. Прерывания по лимитам
   фиксируются как событие, а не скрываются.
4. **Проверки.** После агента запускаются те же команды, что и для человека:
   сначала scoped-проверки, при успехе — `pnpm run check:all`.
5. **Артефакты.** Сохраняются: `git diff`, вывод проверок, время, число
   вмешательств, заметки ревьюера.
6. **Слепое ревью.** Диффы перемешиваются и обезличиваются; ревьюер
   оценивает по рубрике (раздел 7), не зная модель.

Рекомендуемая раскладка артефактов:

```
docs/agent-eval/<YYYY-MM-DD>/
  participants.md
  tasks.md
  <task-id>/<model>/diff.patch
  <task-id>/<model>/checks.txt
  <task-id>/<model>/notes.md
  results.csv
```

## 6. Метрики

### 6.1. Основные

| Метрика              | Как считать                                            |
| -------------------- | ------------------------------------------------------ |
| First-pass pass rate | доля прогонов, где проверки зелёные без правок агента  |
| Accepted rate        | доля задач, принятых ревьюером без изменения поведения |
| Rework ratio         | строки правок ревьюера / строки диффа агента           |
| Review time          | минуты ревью до принятия или отказа                    |
| Invariant violations | нарушения инвариантов проекта за задачу                |
| Regressions          | тесты, ставшие красными после диффа                    |

Инварианты для подсчёта (из `AGENTS.md`): клиент не валидирует правила,
сервер не доверяет клиентским объектам, нет прямого `console`, нет `any` и
non-null assertion, не ослаблены проверки типов, сохранения сохраняют
миграции, временное состояние не пишется в сейв.

### 6.2. Вспомогательные

- Размер диффа: файлы и строки против ожидаемого объёма.
- Качество тестов: добавлены ли осмысленные поведенческие проверки.
- Время до первого зелёного прогона.
- Токены / стоимость на принятую задачу.
- Число прерываний по лимитам и потерь контекста.
- «Тихие» ошибки: проверки зелёные, но поведение неверно и поймано ревью.

## 7. Рубрика приёмки

Оценка за задачу — целое 1–5, с якорями:

| Балл | Якорь                                                    |
| ---- | -------------------------------------------------------- |
| 1    | Неприемлемо: неверное поведение или сломанные инварианты |
| 2    | Работает после существенных правок ревьюера              |
| 3    | Принято после мелких правок                              |
| 4    | Принято как есть, соответствует конвенциям               |
| 5    | Принято и улучшило решение без лишнего объёма            |

Ревьюер ставит балл до разглашения модели. Спорные случаи описываются
текстом, а не подгоняются под число.

## 8. Таблица результатов

Одна строка — один прогон:

```csv
task_id,type,model,run,first_pass,accepted,rubric,rework_ratio,review_min,invariants,regressions,notes
```

Сводка по модели:

| Метрика                | Модель A | Модель B |
| ---------------------- | -------- | -------- |
| First-pass pass rate   |          |          |
| Accepted rate          |          |          |
| Медиана rubric         |          |          |
| Медиана review time    |          |          |
| Rework ratio (медиана) |          |          |
| Invariant violations   |          |          |
| Regressions            |          |          |

Сравнивай **попарно по задачам** (win/loss/tie), а не только средние:
средние по 8–12 задачам легко вводят в заблуждение. Указывай N и честно
пиши, что при таком объёме выборки разница в несколько процентных пунктов
неотличима от шума.

## 9. Шаблон промпта

```
Задача: <однозначная цель и критерий готовности>.
Контекст: <ссылки на файлы, разделы PRODUCTION_READINESS.md>.
Ограничения:
- следуй AGENTS.md и локальным конвенциям;
- минимальный связный дифф, без несвязанных правок;
- не коммить, не пушить, не менять проверки ради прохождения;
- новые типы без any и non-null assertion;
- если требование неоднозначно — задай вопрос, не угадывай.
Проверки: <scoped-команды>, затем pnpm run check:all.
В конце: что изменено, какие проверки запущены, что не проверено.
```

## 10. Честность измерения

Учитывай и по возможности нейтрализуй:

- **Лимиты и обрывы.** Rate limit рвёт сессию сильнее, чем разница моделей.
- **Разогрев и усталость.** Рандомизируй порядок, давай одинаковый старт.
- **Обновления моделей.** Зафиксируй версию и дату; не сравнивай «модель
  вообще», сравнивай конкретный срез.
- **Утечка контекста.** Агент мог видеть репозиторий и историю; по
  возможности используй свежие задачи.
- **Смещение ревьюера.** Слепые диффы, заранее зафиксированная рубрика.
- **Разные инструменты.** Одинаковые права, файлы правил и MCP-доступ.
- **Самоотчёт агента.** «Все тесты прошли» не считается доказательством:
  верь только выводу команд.

## 11. Решение по итогам

Модель B заменяет A, только если одновременно:

1. First-pass pass rate не хуже более чем на 10 п.п.
2. Медиана рубрики не ниже.
3. Rework ratio и review time не выше (в пределах шума).
4. Нет роста нарушений инвариантов и регрессий.
5. Выигрыш в стоимости или доступности подтверждён.

Иначе оставляем текущий инструмент. При смешанной картине фиксируй, на каких
типах задач какая модель сильнее, и распределяй задачи, а не выбирай
«победителя вообще».

## 12. Ограничения

- Это методология, а не отчёт: здесь нет и не должно быть цифр о конкретных
  моделях.
- Публичные бенчмарки не заменяют прогон: они не знают инвариантов проекта.
- При N < 8 выводы считаются предварительными и не основанием для смены
  инструмента.
