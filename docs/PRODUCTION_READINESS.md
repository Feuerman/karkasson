Дата анализа: 2026-11-05
Статус: анализ завершён; этап 0, п. 1.1–1.5, 2.1–2.5 выполнены
Область: клиент `src/`, сервер `server/src/`, тесты, CI, эксплуатация

Документ фиксирует разрывы между текущим состоянием проекта и требованиями
публичного продукта: безопасность, надёжность, масштабирование, удобство,
доступность, юридические риски и проверки. Пункты сгруппированы по приоритетам.

## Как читать

- **P0** — блокирует публичный запуск: уязвимость, потеря данных или
  невозможность восстановиться после сбоя.
- **P1** — нужно для приемлемого опыта широкой аудитории; можно выпустить
  следом, но до активного маркетинга.
- **P2** — развитие, полировка, снижение стоимости владения.
- **[Добавить]**, **[Изменить]**, **[Удалить]** — характер работы.
- **[Сделано]** — пункт выполнен; рядом зафиксированы инварианты и handoff.
- Ссылки на файлы даны для быстрого входа в контекст, а не как обязательный
  список правок.

## Краткий вывод

Ядро проекта сильное: сервер — источник истины, команды проходят через ack,
есть сохранения, миграции, интеграционные тесты и браузерные сценарии. Но
публичный запуск сейчас ограничивают:

1. отсутствие настоящей идентичности: `deviceId` приходит от клиента и
   рассылается всем;
2. отсутствие защиты периметра: rate limiting, валидация payload, проверка
   Origin, Firebase Security Rules;
3. отсутствие i18n и полноценного восстановления соединения;
4. отсутствие эксплуатационного контура: деплой сервера, метрики, алерты,
   резервные копии;
5. юридические риски названия, правил и оформления.

## 1. Безопасность

### 1.1. Идентичность и сессии — P0

- **[Сделано] Не доверять `deviceId` из клиента.** Клиентские идентификаторы
  больше не являются доказательством владения слотом: сервер выдаёт
  HMAC-подписанный токен сессии, а `RejoinGame` и команды используют
  привязанный к сокету `sessionId`.
- **[Сделано] `deviceId` и `socketId` убраны из публичных payload'ов.**
  Публичный `PlayerView` содержит только `id`, `name`, `color`, `score`,
  `sessionId`, `isConnected`; `socketId` остаётся внутренним серверным
  runtime-полем и при сериализации принудительно обнуляется.
- **[Сделано] Серверная сессия.** Токен формата
  `v1.<sessionId>.<issuedAt>.<HMAC-SHA256>`, stateless: сервер не хранит
  сессии и переживает рестарт. `SESSION_SECRET` обязателен в production
  (не короче 32 символов); для dev/test есть фиксированный fallback. Клиент
  хранит токен в `localStorage` под ключом `sessionToken`. TTL и отзыв токенов
  пока не реализованы.
- **[Сделано] Публичный идентификатор для определения своего игрока.**
  Вместо `isSelf` клиент сравнивает публичный `sessionId`; знание этого
  идентификатора не даёт прав без валидного токена.
- **[Сделано] Проверка прав на команды.** Команды слотов проверяют владельца
  через `sessionId`, запуск игры — владельца лобби, игровые команды и
  предпросмотр — текущего игрока по привязанному сокету; `RejoinGame`
  восстанавливает только слоты своей сессии.
- **[Сделано] Регрессионные тесты на захват слота.** Интеграционные тесты
  проверяют, что чужой клиент не восстанавливает слот по публичному
  `sessionId`, а сервер отклоняет такой `RejoinGame`.

Инварианты этапа:

- `sessionId` — публичный UUID без прав; аутентификация — только
  HMAC-токен.
- `socketId` — только runtime-поле; в сохранениях обнуляется, в сводки и
  публичные события не попадает.
- Схема сохранений 9: миграция удаляет `deviceId` и ставит
  `sessionId = null`. Старые активные партии после деплоя не наследуют
  сессии и не могут быть продолжены — это осознанный разрыв, а не баг.
- Компьютерный игрок: `!socketId && !sessionId` на сервере, `!sessionId`
  на клиенте.
- Клиент ждёт `RegisterSession` перед первыми командами; при разрыве
  незавершённые ack отклоняются сообщением о прерванном соединении.

Handoff:

- Production-деплой обязан задать `SESSION_SECRET`; смена секрета
  инвалидирует все выданные токены.
- TTL/отзыв токенов — в разделе 7; rate limiting и валидация payload —
  п. 1.2.
- `TestClient` хранит токены по identity, а не по URL: тестовый сервер
  меняет порт при рестарте, а сценарий persistence переиспользует identity
  после перезапуска.
- Проверено: `pnpm test`, `pnpm run test:coverage`, `pnpm run type-check`,
  `pnpm run lint`, `pnpm run build`, `pnpm --filter server run build`.
  Браузерный smoke не запускался.

### 1.2. Валидация и защита от злоупотреблений — P0

- **[Сделано] Runtime-валидация всех входящих событий.** Обработчики получают
  payload как `unknown` и разбирают его едиными парсерами до вызова домена:
  проверяются форма, типы, `null`, диапазоны координат и слотов, длина строк,
  идентификаторы и допустимые enum-значения. Невалидный payload даёт
  `CommonErrors.InvalidRequest` и не меняет состояние.
- **[Сделано] Лимиты.** Частота команд ограничена на сокет и IP, число
  создаваемых лобби — на сессию и на сервер, имя — по длине. Заданы
  `maxHttpBufferSize`, максимум сокетов на IP и общий предел партий.
- **[Сделано] Защита от brute force 6-значного `roomCode`.** Неудачные входы
  считаются по IP за окно времени: после серии появляется задержка, затем
  временная блокировка; события попадают в серверный журнал.
- **[Сделано] Ограничения имён.** Имя нормализуется по Unicode, чистится от
  управляющих и невидимых символов, схлопывает пробелы, ограничивается
  24 символами, проверяется на нецензурную лексику и дубликаты без учёта
  регистра и «ё». Пустое значение оставляет компьютерное имя по умолчанию.
- **[Сделано] Валидация токена по длине и формату.** Слишком длинные токены,
  пробельные и управляющие символы отклоняются до проверки подписи; HMAC
  проверяется только для строк допустимого формата.
- **[Сделано] Глобальные обработчики ошибок процесса.**
  `uncaughtException`/`unhandledRejection` пишут инцидент в журнал и
  запускают штатную остановку: закрытие сокетов, сброс партий, выход.
- **[Сделано] Ошибки не раскрывают внутренние детали.** В ack уходит
  безопасный текст из каталога и стабильный машинный код (`каталог.ключ`);
  стек и служебные сообщения остаются только в серверном журнале.

Инварианты этапа:

- Любое входящее событие проходит парсер из
  `server/src/socket/validation.ts`; обработчик не деструктурирует payload
  напрямую. `null` допустим только там, где означает отсутствие
  необязательных опций.
- Ошибка в ack имеет вид `{ error, code }`; код строится из ключа каталога
  (`common.invalid_request`, `lobby.player_name_taken` и т. п.), поэтому
  переименование ключа меняет публичный код.
- Лимиты по умолчанию: 40 команд на сокет и 120 на IP с пополнением
  20/60 в секунду; 64 КиБ на пакет; 20 сокетов на IP; 500 партий в памяти;
  5 незапущенных лобби на сессию.
- Перебор `roomCode`: окно 10 минут, задержка после 3 неудач, блокировка
  после 8 на 10 минут. Задержка и блокировка считаются по IP.
- `X-Forwarded-For` учитывается только при `TRUST_PROXY=true`. За обратным
  прокси без этой настройки все клиенты выглядят одним IP.
- Имя: NFKC, ≤24 code points, запрещены управляющие/форматные символы,
  нецензурная лексика; дубликаты сравниваются нормализованно.
- Токен сессии: не длиннее 512 символов, без пробелов и управляющих
  символов; иначе сессия не восстанавливается и выдаётся новая.
- Остановка после необработанной ошибки идёт через общий `handle.close()`,
  а не через немедленный `process.exit` из обработчика.

Handoff:

- Лимиты и счётчики живут в памяти одного экземпляра сервера. Для
  multi-instance нужен общий limiter (этап 2).
- Пороговые значения не вынесены в переменные окружения, кроме
  `TRUST_PROXY`; менять их следует в `config.ts` и `abuseGuard.ts` осознанно.
- Капча не реализована: защита от перебора — задержка, блокировка и журнал.
- При добавлении события нужно добавить парсер и использовать его в
  обработчике; новые сообщения — только в каталог `modules/errors.ts`.
- Проверено: `pnpm test`, `pnpm run test:coverage`, `pnpm run type-check`,
  `pnpm run lint`, `pnpm run build`, `pnpm --filter server run build`.
  Браузерный smoke не запускался.

### 1.3. Транспорт, CORS и WebSocket — P0/P1

- **[Сделано] CORS и список Origin клиента.** `CLIENT_ORIGIN` (список через
  запятую) задаёт разрешённые Origin; без переменной в production используется
  публичный `https://feuerman.github.io`, в разработке и тестах — локальные
  значения по умолчанию и loopback-Origin. CORS применяется к polling и
  рукопожатию; клиент больше не привязан к `transports: ['websocket']`,
  начинает с polling и переходит на WebSocket.
- **[Сделано] Проверка Origin при рукопожатии.** `allowRequest` Socket.IO
  отклоняет браузерное рукопожатие с неизвестным Origin до регистрации
  сокета; запросы без Origin (серверные клиенты и тесты) допускаются.
- **[Сделано] Security headers и HTTPS.** Сервер отдаёт CSP,
  `X-Content-Type-Options`, `X-Frame-Options`, `Referrer-Policy` и
  `Permissions-Policy`; HSTS — при защищённом соединении или в production.
  `trust proxy` включается через `TRUST_PROXY`. Production-сборка клиента
  получает CSP meta с `connect-src` на сервер, запретом внешних скриптов и
  `upgrade-insecure-requests` для HTTPS; referrer-политика задана и в
  `index.html`.
- **[Сделано] Admin UI в production.** По умолчанию включён только вне
  production; в production требует явного `SOCKET_ADMIN_UI_ENABLED=true` и
  настроенных учётных данных. Origin админки добавляется в allowlist только
  когда UI включён.
- **[Сделано] `/health` и диагностика.** Публичный `/health` отдаёт только
  `{ status: 'ok' }`. Подробное состояние хранилища доступно на
  `/health/details` по `Authorization: Bearer $HEALTH_TOKEN`; без токена
  endpoint отвечает 404, с неверным токеном — 401.
- **[Сделано] Таймауты HTTP/WebSocket.** Заданы ping/pong, upgrade и connect
  timeouts Socket.IO, а также `requestTimeout`/`headersTimeout` HTTP-сервера.

Инварианты этапа:

- Origin сравниваются в каноническом виде; неизвестный Origin отклоняется,
  запрос без Origin считается не браузерным и допускается.
- `CLIENT_ORIGIN` не может быть `*` или не-http(s) значением: такие записи
  игнорируются с предупреждением, чтобы опечатка в необязательной настройке не
  останавливала сервер. Если валидных Origin не осталось, в production
  разрешён только публичный адрес клиента проекта, вне production — локальные.
  Loopback-Origin автоматически разрешены только вне production.
- Origin `https://admin.socket.io` входит в allowlist только при включённом
  Admin UI.
- Публичный `/health` не содержит `StorageStatus`; токен диагностики
  сравнивается за постоянное время и не попадает в журнал.
- CSP клиента строится при сборке из `VITE_SERVER_URL`; production-значение
  по умолчанию — HTTPS-адрес сервера.

Handoff:

- Для переопределения Origin клиента задайте `CLIENT_ORIGIN` (список через
  запятую); по умолчанию в production используется `https://feuerman.github.io`.
  При работе за Render нужен `TRUST_PROXY=true`; также нужны `SESSION_SECRET`
  и, при использовании диагностики, `HEALTH_TOKEN`.
- Для Admin UI в production нужно явно включить `SOCKET_ADMIN_UI_ENABLED` и
  задать пару `SOCKET_ADMIN_UI_USERNAME`/`SOCKET_ADMIN_UI_PASSWORD_HASH`.
  По умолчанию админка на публичном сервере недоступна.
- Внешние Google Fonts пока остаются: CSP разрешает `fonts.googleapis.com` и
  `fonts.gstatic.com`. Self-hosting шрифтов — задача этапа 2.
- Браузерные тесты поднимают Vite на случайном loopback-порту, поэтому в
  тестовом окружении Origin проверяется по loopback-правилу. В production это
  правило отключено.
- Проверено: `pnpm --filter server run build`, `pnpm run type-check`,
  `pnpm run lint`, `pnpm run build`, целевые unit/integration-тесты и
  `tests/browser/lobby.spec.ts`. Полный `pnpm run check:all` — перед релизом.

### 1.4. Firebase и данные — P0

- **[Сделано] Security Rules в репозитории.** `database.rules.json` разрешает
  чтение и запись только серверу с claim `server: true`; остальные пути и
  клиентский доступ закрыты по умолчанию. `firebase.json` связывает правила с
  проектом, деплой — `npx firebase-tools deploy --only database`.
- **[Сделано] Запись только с сервера.** Сервер входит в Firebase Auth по
  custom token, подписанному ключом сервисного аккаунта
  (`FIREBASE_SERVICE_ACCOUNT`), и работает с базой от этого пользователя.
  Клиент не подключается к Firebase напрямую и не может читать или менять игры.
- **[Сделано] Изоляция окружений.** Конфигурация требует согласованные
  `FIREBASE_API_KEY`, `FIREBASE_DATABASE_URL` и сервисный аккаунт. README
  фиксирует отдельные проекты для dev/staging/prod и запрет production-ключей
  в локальных файлах; ключи сервисных аккаунтов добавлены в `.gitignore`.
- **[Сделано] Инструкция по бэкапам и восстановлению.** README описывает
  ежедневный экспорт, срок хранения и ежемесячную проверку восстановления в
  staging. Регулярный запуск и хранение копий — задача эксплуатации.
- **[Сделано] Инструкция по аудиту доступа.** README требует 2FA, журнал
  административных операций, Cloud Audit Logs и сохранение серверных журналов
  без payload'ов и секретов. Настройка журналов — задача эксплуатации.

Инварианты этапа:

- Безопасность не держится на сокрытии конфигурации: `FIREBASE_API_KEY`
  публичен, доступ к данным даёт только подпись сервисного аккаунта.
- Custom token живёт час; обновлением ID token занимается Firebase SDK.
  Смена или отзыв ключа сервисного аккаунта закрывает серверу доступ.
- Правила не меняют путь хранения `games/<id>`: существующие сохранения
  читаются без миграции.
- В production без `FIREBASE_SERVICE_ACCOUNT` сервер не стартует с понятной
  ошибкой; в dev/test остаётся in-memory хранилище.

Handoff:

- Перед деплоем: создать ключ сервисного аккаунта, задать три `FIREBASE_*`
  переменные в панели хостинга, применить `database.rules.json` и проверить,
  что прямой REST-запрос с API key получает отказ, а сервер загружает партии.
- Старые необязательные `FIREBASE_AUTH_DOMAIN`, `FIREBASE_PROJECT_ID` и
  подобные переменные серверу больше не нужны.
- Бэкапы, retention, тестовое восстановление и аудит настраиваются в Firebase
  Console и на хостинге по инструкции README; код их не заменяет.
- Проверено: `tests/unit/database.test.ts`, `pnpm --filter server run build`,
  `pnpm run type-check`, ESLint по изменённым файлам. Полный
  `pnpm run check:all` — перед релизом.

### 1.5. Прочее

- **[Сделано] Политика ответственного раскрытия уязвимостей.** `SECURITY.md`
  описывает приватный канал GitHub Security Advisories, состав сообщения,
  сроки ответа, область действия и безопасную гавань.
- **[Сделано] Автоматические проверки безопасности в CI.**
  `.github/workflows/security.yml` запускает аудит зависимостей
  (`pnpm audit --audit-level high`), поиск секретов (gitleaks) и CodeQL для
  JavaScript/TypeScript; дополнительно workflow идёт по расписанию раз в
  неделю.
- **[Сделано] Проверка XSS.** В клиентском коде нет `v-html`, `innerHTML`,
  `outerHTML`, `insertAdjacentHTML` и `document.write`; имена игроков
  выводятся обычной интерполяцией Vue и экранируются. CSP production-сборки
  запрещает внешние скрипты (`script-src 'self'`). Регрессия закреплена
  `tests/unit/xssSafety.test.ts`.
- **[Сделано] Аудит журналов.** Серверный и клиентский логгеры получают только
  тип события, идентификаторы игры/игрока и текст ошибки. Токены сессии,
  `deviceId`, полные payload'ы и содержимое сохранений в журналы не попадают;
  IP пишется только в сообщениях об ограничениях и блокировках.
- **[Сделано] Ограничение частоты создания игр с ИИ.** Запуск полностью
  автоматической партии проходит отдельный лимит по IP, а число одновременных
  таких партий ограничено глобально и на сессию. При отказе игрок получает
  понятное сообщение.

Инварианты этапа:

- Приватные сообщения об уязвимостях не дублируются в открытых issue.

## 2. Надёжность и сохранность данных

### 2.1. Сохранения и очередь команд — P0

- **[Сделано] `LeaveGame` для начатой партии сохраняет состояние.** Выход
  проходит через очередь команд партии: изменение освобождает сокет, затем
  состояние пишется в БД и только после этого публикуется и подтверждается.
  Ошибка записи откатывает изменение и возвращает `SaveFailed`.
- **[Сделано] Безопасный порядок удаления.** `deleteGame` убирает партию из
  памяти, ставит удаление в очередь после сохранений и при ошибке БД
  возвращает партию и владельца в память. Повторные вызовы удаления
  объединяются, поэтому запись не «воскресает» после перезапуска.
- **[Сделано] Retry/timeout/backoff для Firebase.** Каждая операция с
  хранилищем ограничена таймаутом и повторяется с экспоненциальной паузой;
  отказы прав и некорректные данные не повторяются. Параметры задаются
  `FIREBASE_OPERATION_TIMEOUT_MS`, `FIREBASE_OPERATION_ATTEMPTS` и
  `FIREBASE_RETRY_BASE_DELAY_MS`.
- **[Сделано] Ограничение и мониторинг очереди.** На партию допускается не
  больше 20 ожидающих записей; переполнение даёт понятный `SaveFailed`.
  `storageStatus()` отдаёт число ожидающих операций, возраст самой старой,
  число ошибок записи и число команд в очереди.
- **[Сделано] Идемпотентность команд.** Клиент прикладывает `commandId` к
  изменяющим игровым командам, сервер помнит успешные ключи 10 минут
  (не больше 200 на партию). Повтор возвращает текущее состояние, но не
  применяет ход второй раз; транзиентный предпросмотр не кэшируется.
- **[Сделано] Ошибки фоновых задач не теряются.** Очередь сохранений не
  блокируется упавшей записью: следующая команда получает собственную
  попытку, а ошибки считаются и превращаются в `SaveFailed` для игрока.

Инварианты этапа:

- Перед ack изменяющей команды новое состояние уже записано; исключение —
  только транзиентный предпросмотр поворота и клетки.
- `saveGame` сериализует снимок сразу и ставит записи одной партии в очередь;
  ошибка предыдущей записи не отменяет следующую.
- Удаление идемпотентно: при сбое БД состояние остаётся в памяти, а не
  восстанавливается из устаревшей записи после рестарта.
- `commandId` уникален в пределах команды и партии; повтор с тем же ключом
  после таймаута ack безопасен. Ключ живёт в памяти и не переживает рестарт.
- Таймауты и повторы живут в Firebase-реализации `IGameDatabase`, а не в
  `GameService`: тестовые хранилища сохраняют управляемые сбои.

Handoff:

- Автоматический повтор команды клиентом появится в п. 2.3; при нём нужно
  переиспользовать исходный `commandId`, а не создавать новый.
- Ограничение очереди — защита от медленного хранилища, а не замена
  деградации: после исчерпания повторов команда по-прежнему откатывается.
- `storageStatus()` расширен полями `pendingSaveOperations`,
  `oldestSaveAgeMs` и `saveFailures`; они уже отдаются защищённым
  `/health/details`.
- Проверено: `pnpm test` (полный набор), `pnpm run type-check`,
  `pnpm run lint`, `pnpm run build`, `pnpm --filter server run build`.
  Браузерный smoke не запускался.

### 2.2. Загрузка и жизненный цикл партий — P0/P1

- **[Сделано] Сводки и ленивая загрузка.** Заголовки партий хранятся в
  отдельном узле и пишутся вместе с состоянием. При старте поднимаются только
  незавершённые партии; завершённая загружается по требованию, когда игрок
  открывает результат. Миграция старого хранилища собирает сводки один раз.
- **[Сделано] Список лобби без разбора сохранений.** `formatGamesList()` и
  `getGameSummaries()` собирают память и кэш заголовков, не читая весь узел
  игр. Счётчик нечитаемых сохранений сохраняется.
- **[Сделано] Безопасный жизненный цикл.** Активная партия удаляется только
  когда в ней нет подключённых людей и истёк конфигурируемый срок
  заброшенности; партия с подключённым игроком не трогается. Завершённые
  партии удаляются по сроку хранения, в том числе ленивые сводки.
- **[Сделано] Причины удаления.** Событие удаления передаёт `stale`,
  `owner_left`, `expired` или `failed`; клиент показывает понятное сообщение
  и возвращает игрока в список партий.
- **[Сделано] Пауза при отключении.** Короткое отключение человека
  приостанавливает ходы компьютера и не удаляет партию. Заброшенную партию
  позже убирает общая очистка. Явный выход из начатой партии сохраняет
  освобождение слота.
- **[Сделано] Передача прав владельца.** При выходе создателя до старта права
  переходят следующему оставшемуся игроку; пустое лобби удаляется. Клиент
  определяет создателя по серверному полю, а не по первому слоту.
- **[Сделано] Корректное завершение.** Остановка закрывает приём команд,
  дожидается уже принятых команд партии, отменяет таймеры компьютера и
  сбрасывает состояние на диск.

Инварианты этапа:

- Сводка — компактный заголовок; полное состояние читается только для работы
  с партией.
- Партия без подключённых игроков — не повод удалять её сразу: срок
  заброшенности задаётся отдельно и по умолчанию равен суткам.
- Завершённая партия хранится ограниченное время; удаление по сроку работает
  и для партий, которые не загружались в память.
- Владелец лобби всегда известен серверу; после перезапуска он
  восстанавливается по первому занятому слоту.

Handoff:

- Сроки задаются `GAME_ABANDONED_TIMEOUT_MS` и
  `FINISHED_GAME_RETENTION_MS`; значения по умолчанию — сутки и неделя.
- Индекс сводок загружается целиком, но содержит только заголовки. При
  заметном росте числа комнат следующим шагом будет пагинация списка.
- Узел сводок закрыт теми же server-only правилами, что и сохранения. При
  деплое примените обновлённый `database.rules.json`, иначе запись индекса
  будет отклонена.
- Проверено локально: `pnpm test`, `pnpm run test:coverage`,

  `pnpm --filter server run build`. Полный `pnpm run check:all` — за

### 2.3. Переподключение клиента — P1

- **[Сделано] Бесконечные попытки с backoff.** Клиент не сдаётся после
  10 попыток: Socket.IO повторяет подключение с паузой до 5 секунд, а явное
  отключение сервером перезапускается тем же путём. На всех экранах есть
  компактный индикатор, а при простое — полноэкранное состояние с кнопкой
  «Переподключиться».
- **[Сделано] Автоматический rejoin.** После подтверждения сессии — при первом
  запуске, обновлении страницы и восстановлении соединения — клиент отправляет
  `RejoinGame` для последней начатой партии. Явный выход очищает метку, поэтому
  игрок не возвращается в покинутую игру.
- **[Сделано] Разные причины простоя.** Интерфейс различает отсутствие
  интернета, недоступность сервера, таймаут и закрытие соединения сервером;
  технические подробности остаются в журнале.
- **[Сделано] Обработка `connect_error`.** Ошибка рукопожатия переводит клиента
  в режим повторных попыток и показывает понятный текст и номер попытки вместо
  пустого экрана.
- **[Сделано] Тесты.** Интеграционные сценарии проверяют автоматическое
  переподключение с повторным занятием слота, ручную попытку, холодный старт
  сервера и повторный rejoin; браузерный сценарий — возврат в партию после
  перезагрузки. Unit-тесты покрывают тексты и категории состояния.

Инварианты этапа:

- `GameService` остаётся единственным местом, где живут попытки, фаза
  соединения, причина обрыва и ручной retry.
- `sessionReady` публикуется только после успешной регистрации сессии;
  автоматический rejoin запускается ровно один раз на подтверждение сессии.
- При сетевой ошибке метка последней партии сохраняется — следующее
  переподключение повторит rejoin. Терминальные отказы
  (`common.game_not_found`, `common.player_not_found_in_game`) очищают метку и
  локальное состояние.
- Явный выход из партии, возврат в лобби и «Сыграть ещё» очищают `lastGameId`,
  иначе обновление страницы вернуло бы игрока в покинутую игру.
- `disconnect()` — ручное отключение: автоматического переподключения нет,
  пока клиент не вызовет `connect` или `reconnectNow`.

Handoff:

- Пауза переподключения и таймаут рукопожатия заданы в
  `modules/GameService.ts`; при их изменении синхронизируйте тексты состояния.

### 2.4. Игровой процесс и ИИ — P1

- **[Сделано] Минимум игроков для старта.** `startGame` требует минимум двух
  игроков с именем; иначе сервер возвращает понятную ошибку и не создаёт
  партию. Проверка живёт и в обработчике (`lobbyStartError`), и в самом
  `startGame`, поэтому прямой вызов сервиса также не запускает недопустимую
  игру.
- **[Сделано] Политика автоматических партий после перезапуска.** `resumeAll`
  возобновляет не больше `MAX_ACTIVE_AI_GAMES` полностью автоматических партий;
  лишние удаляются с причиной `stale`, чтобы не занимать память и цикл событий
  без наблюдателей. Смешанные партии и партии людей возобновляются как раньше.
- **[Сделано] Проверка синхронного расчёта ИИ.** Замер полной партии из четырёх
  компьютеров: 69 вызовов поиска хода, среднее ~14 мс, худший ход ~50 мс, вся
  партия ~1.1 с на текущей машине. Worker и ограничение сложности не нужны;
  watchdog страхует асинхронные зависания.
- **[Сделано] Watchdog хода ИИ.** Каждый ход ограничен
  `COMPUTER_MOVE_WATCHDOG_MS` (по умолчанию 30 с). При превышении партия
  удаляется, клиенты получают `GameError` и `GameDeleted` с причиной `failed`,
  а планировщик больше не пытается продолжать её ходы.
- **[Сделано] Криптостойкая случайность.** Перемешивание колоды и вставка
  отложенных тайлов используют `crypto.randomInt`, идентификаторы игровых
  объектов — `crypto.randomUUID`. Воспроизводимость не требуется, seed не
  хранится.
- **[Сделано] Мультивкладки и одно устройство.** Сессия привязана к одному
  активному сокету: новая вкладка забирает управление, получает уже занятые
  слоты без второго слота, а прежняя получает `SessionReplaced`, отключается и
  не переподключается автоматически. Повторный вход той же сессии идемпотентен.

Инварианты этапа:

- Партия начинается только при двух и более игроках с именем.
- После перезапуска автоматических партий возобновляется не больше глобального
  предела; остальные удаляются, а не продолжают занимать ресурсы.
- Watchdog удаляет только зависшую текущую партию; синхронный расчёт он
  прервать не может, поэтому расчёт проверяется отдельно замером.
- В серверном коде нет `Math.random` для колоды и идентификаторов игровых
  объектов.
- У сессии один активный сокет: последняя вкладка побеждает, старая теряет
  управление и автоматически не возвращается. Сессия не занимает два слота.

Handoff:

- Порог watchdog задаётся `COMPUTER_MOVE_WATCHDOG_MS`; удаление партии после
  срабатывания необратимо.
- Если сложность ИИ заметно вырастет, синхронный расчёт придётся вынести в
  worker: таймер watchdog не срабатывает, пока цикл событий занят.
- Удаление лишних автоматических партий после рестарта — осознанная потеря
  невидимых партий; владельца у них после перезапуска нет.
- При ручном переподключении старая вкладка снова забирает сессию; это
  политика «последняя вкладка побеждает».
- Проверено: `pnpm test`, `pnpm run test:coverage`, `pnpm run type-check`,
  `pnpm run lint`, `pnpm run build`, `pnpm --filter server run build`.
  Браузерный smoke не запускался.

### 2.5. Версионирование и совместимость — P1

- **[Сделано] Handshake версии протокола.** Константа `PROTOCOL_VERSION`
  (`server/src/modules/types.ts`) общая для клиента и сервера. Сервер
  отдаёт `protocolVersion` в ответе на `RegisterSession`; клиент присылает
  свою версию и при несовпадении блокирует все команды и требует
  перезагрузки страницы.
- **[Сделано] Политика миграций и обратной совместимости.** Схема сохранений
  — версия 9 (`GAME_SAVE_SCHEMA_VERSION`). `deserializeGameState` читает
  версии 1–9 и мигрирует старые форматы (`migrateLegacyGameState`), а
  неизвестную версию отвергает с ошибкой. Покрыто тестами round-trip и
  миграции старых версий (1, 4, 5, 6, 8 → 9) и отказом от версии 99.
- **[Сделано] Version endpoint.** `GET /version` отдаёт `{ server, protocol }`
  — версию сервера из `package.json` и версию протокола; клиентская версия
  доступна через `VITE_APP_VERSION` (фолбэк `dev`).

Инварианты этапа:

- `PROTOCOL_VERSION` меняется только при необратимых изменениях формата
  событий или ответов; клиент с более старой версией должен обновить
  страницу перед отправкой команд.
- Старые схемы сохранений остаются читаемыми; версия в
  `SUPPORTED_SCHEMA_VERSIONS` не удаляется, пока такие записи ещё могут
  встречаться в хранилище.
- Неизвестная версия сохранения не загружается молча: ошибка десериализации
  попадает в журнал, а партия не восстанавливается из незнакомого формата.
- Клиентская версия для диагностики берётся из `VITE_APP_VERSION` хостинга;
  локально и в тестах — `dev`.

Handoff:

- Перед выкаткой новой `PROTOCOL_VERSION` согласовать с клиентом: старые
  вкладки получат требование перезагрузки, а не молчаливую несовместимость.
- Откат схемы сохранений: не удалять предыдущую версию из
  `SUPPORTED_SCHEMA_VERSIONS` и не отменять `GAME_SAVE_SCHEMA_VERSION` назад,
  пока старые записи могут быть в хранилище; при откате деплоя сервера
  клиенты со старой версией протокола продолжат работать до принудительного
  обновления страницы.
- Проверено: `pnpm test`, `pnpm run test:coverage`, `pnpm run type-check`,
  `pnpm run lint`, `pnpm run build`, `pnpm --filter server run build`.

## 3. Масштабирование и эксплуатация

### 3.1. Один инстанс или несколько — P0/P1

- **[Сделано] Подтверждён single-instance режим.** Реестр партий в памяти,
  стандартный Socket.IO (in-memory) adapter и сохранения last-write-wins.
  Горизонтальное масштабирование без доработки приведёт к потере команд и
  «раздвоению» партий.
- **[Сделано] Режим зафиксирован: один инстанс с защитой от параллельного
  деплоя.** Выбран наименее рискованный путь — single-instance, а не Redis
  adapter + распределённые блокировки. Второй процесс не может стартовать,
  пока первый hält актуальную блокировку инстанса.
- **[Сделано] Защита от двух инстансов на одной БД.** Instance lock в узле
  `instanceLock` корня хранилища: владелец обновляет heartbeat, второй процесс
  получает отказ при старте, а после истечения `INSTANCE_LOCK_STALE_MS`
  блокировку можно забрать (защита от аварийного завершения и деплоя Render).
- **[Сделано] Тест блокировки инстанса.** `tests/unit/instanceLock.test.ts`
  проверяет, что второй процесс не стартует при актуальной блокировке, что
  освобождение чужой блокировки игнорируется, и что устаревшую блокировку
  можно забрать.

### 3.4. Производительность — P2

- **[Изменить] Не отправлять всю историю действий на каждый ход.**

## 10. Проверки

Код приложения в рамках анализа не менялся, поэтому обязательные проверки не
запускались. Перед итоговым изменением использовать:

Документ является планом, а не утверждённым дизайном: перед реализацией
пунктов, меняющих протокол, сохранения или игровое поведение, нужно
согласовать решение и обновить `AGENTS.md`/тесты.
