# Готовность «Каркассона» к широкой аудитории

Дата анализа: 2026-11-05
Статус: анализ завершён; этап 0, п. 1.1–1.5, 2.1–2.5, 4.1, 5.2 выполнены
Область: клиент `src/`, сервер `server/src/`, тесты, CI, эксплуатация

Документ фиксирует разрывы между текущим состоянием проекта и требованиями
публичного продукта: безопасность, надёжность, масштабирование, удобство,
доступность, юридические риски и проверки. Пункты сгруппированы по приоритетам.

## Как читать

- **P0** — блокирует публичный запуск: уязвимость, потеря данных или
  невозможность восстановиться после сбоя.
- **P1** — нужно для приемлемого опыта широкой аудитории; можно выпустить
  следом, но до активного маркетинга.
- **P2** — развитие, полировка, снижение стоимости владения.
- **[Добавить]**, **[Изменить]**, **[Удалить]** — характер работы.
- **[Сделано]** — пункт выполнен; рядом зафиксированы инварианты и handoff.
- Ссылки на файлы даны для быстрого входа в контекст, а не как обязательный
  список правок.

## Краткий вывод

Ядро проекта сильное: сервер — источник истины, команды проходят через ack,
есть сохранения, миграции, интеграционные тесты и браузерные сценарии. Но
публичный запуск сейчас ограничивают:

1. отсутствие эксплуатационного контура: метрики, алерты, error tracking,
   резервные копии и дашборд стоимости Firebase;
2. недоделанные клиентские и продуктовые функции: приглашения, аккаунты,
   редактирование имени, рейтинг, PWA, шрифты;
3. недопроверенное: contraste доступности, флейки тестов, контраст WCAG AA;
4. юридические риски названия, правил, оформления, конфиденциальности,
   GDPR/152-ФЗ, лицензий.

Всё остальное из п. 1.1–1.5, 2.1–2.5, 4.1, 5.1, 5.3, секции 7 уже
выполнено и не дублируется ниже.

## 3. Масштабирование и эксплуатация

### 3.2. Наблюдаемость — P1

- **[Добавить] Error tracking (Sentry или аналог)** для сервера и клиента,
  с фильтрацией секретов — инфраструктурное решение, остаётся на этапе
  эксплуатации.
- **[Добавить] Алерты** на рост ошибок, недоступность БД, переполнение
  очереди, event-loop lag, падение healthcheck — настраиваются на стороне
  мониторинга по метрикам `/metrics` и endpoint'у `/health`.
- **[Добавить] Дашборд стоимости Firebase** и лимитов; контроль чтений —
  настраивается в консоли Firebase и операционно.

Инварианты этапа:

- Логи не содержат персональных данных: токены сессий, `deviceId`, полные
  payload'ы и содержимое сохранений не попадают в запись.
- `/health` не раскрывает состояние хранилища públicно; детали
  (`storageStatus`, uptime) только на `/health/details` по `HEALTH_TOKEN`.
- Метрики не содержат идентификаторов конкретных игроков и партий; только
  агрегированные счётчики и гейджи.

Handoff:

- В production задать `LOG_FORMAT=json` (по умолчанию), `LOG_LEVEL` и,
  для `/health/details`, `HEALTH_TOKEN`.
- Метрики собираются с `/metrics` мониторинг-системой; алерты
  настраиваются операционно (вне кода).
- Ошибки серверного процесса по-прежнему приводят к штатной остановке
  через `handle.close()` (см. п. 1.2).
- Распределённый трейсинг и error tracking (Sentry) добавляются
  отдельно, если потребуются для эксплуатации.
- Проверено: `pnpm test`, `pnpm run type-check`, `pnpm run lint`,
  `pnpm run build`, `pnpm --filter server run build`.

Файлы: `server/src/utils/logger.ts`, `server/src/metrics/registry.ts`,
`server/src/metrics/httpMiddleware.ts`, `server/src/middleware/requestId.ts`,
`server/src/app.ts`, `server/src/index.ts`, `server/src/services/GameService.ts`,
`server/src/socket/router.ts`, `server/src/socket/handlers/gameCommand.ts`,
`src/utils/logger.ts`, `tests/unit/logger.test.ts`,
`tests/unit/metrics.test.ts`, `tests/integration/app.test.ts`.

### 3.3. Деплой и окружения — P1

- **[Добавить] Резервные копии и проверку восстановления.** Инструкция по
  ежедневному экспорту, сроку хранения и ежемесячной проверке восстановления
  в staging — в `README.md` (раздел Firebase). Автоматизация бэкапов — задача
  эксплуатации, не заменяется кодом.

Инварианты этапа:

- Сервер в production запускается только с Firebase-хранилищем; in-memory
  база допустима только вне production.
- Порт не открывается, пока `validateProductionEnvironment()` не пройдёт;
  отсутствие `SESSION_SECRET` или `FIREBASE_*` — понятная ошибка и выход с
  ненулевым кодом.
- Остановка всегда дренит уже принятые команды и флашит партии перед
  выходом; блокировка инстанса освобождается только своим владельцем.

Handoff:

- Перед деплоем в Render: задать секреты `FIREBASE_API_KEY`,
  `FIREBASE_DATABASE_URL`, `FIREBASE_SERVICE_ACCOUNT`, `SESSION_SECRET`,
  `HEALTH_TOKEN`, `CLIENT_ORIGIN` в панели хостинга; применить
  `database.rules.json`.
- Откат: Redeploy предыдущего коммита в Render или rollback через панель;
  состояние партий сохраняется в Firebase и переживает перезапуск сервера.
- Бэкапы, retention, тестовое восстановление и аудит настраиваются в Firebase
  Console и на хостинге по инструкции README; код их не заменяет.
- Проверено: `pnpm --filter server run build`, `pnpm run type-check`,
  `pnpm run lint`, `pnpm run build`, полный `pnpm test`.

Файлы: `Dockerfile`, `render.yaml`, `.github/workflows/deploy.yml`,
`.npmrc`, `server/src/index.ts`, `server/src/config.ts`,
`server/src/app.ts`, `package.json`, `pnpm-lock.yaml`, `README.md`.

## 4. Клиент, UX и доступность

### 4.3. Продуктовые функции для широкой аудитории — P1/P2

- **[Добавить] ссылки-приглашения** для приватных комнат — пока не реализованы
  (лobby можно создать приватным, но приглашение только по номеру комнаты и паролю).
- **[Добавить] Аккаунты или хотя бы восстановление личности.** Частично:
  привязка сессии к Firebase Auth (Google OAuth, `linkAccount`) и серверный
  метод `restoreAccount` реализованы, но нет клиентского UI для входа по
  коду/ссылке и восстановления доступа после потери `localStorage`. Потеря
  `localStorage` по-прежнему означает потерю доступа к своим партиям.
- **[Добавить] Редактирование имени, аватары/цвета** с валидацией и модерацией.
  Не реализовано: имя и цвет задаются один раз при создании/входе в слот,
  концепции аватара нет.
- **[Добавить] Историю завершённых партий и рейтинг** — если это часть
  продукта; иначе явно ограничить хранение. Частично: внутрипартийная история
  ходов (`GameActionsHistory`), список завершённых партий
  (`showEndedGames`, `gameSummary.ts`) и TTL хранения завершённых партий
  (`FINISHED_GAME_RETENTION_MS`) реализованы. Кросс-сессионной истории
  сыгранных партий и рейтинга игроков нет.

### 4.4. Доступность — P1

- **[Проверить] Контраст, размеры целей, reduced motion, масштабирование.**
  Проверяется вручную: палитра средневековой темы не везде укладывается в
  WCAG AA, поэтому цветовой контраст остаётся предметом ручной проверки,
  а не автоматизированного утверждения.

Инварианты этапа:

- `html[lang]` всегда заполнено текущей локалью; заголовок страницы задаётся.
- Клетка доски с фокусом имеет `role="button"`, доступное имя
  (`aria-label`) и видимый `focus-visible`-индикатор.
- Объявления ходов и ошибок размещения выходят через `aria-live="polite"`
  / `role="alert"`, а не только визуально.
- Автоматические axe-проверки не вводят новых нарушений на странице лобби
  и области доски (кроме theme-уровневого цветового контраста).

Handoff:

- Новые интерактивные элементы получают `role`, `aria-label` и
  `focus-visible`-индикатор; при добавлении модалок — возвращение фокуса и
  закрытие по `Escape`.
- axe-тест дополняется при новых экранах; контраст сверяется вручную перед
  релизом, так как палитра темы не гарантирует соответствие WCAG AA.
- Проверено: `pnpm test:browser` (нужен Chromium), `pnpm run type-check`,
  `pnpm run lint`, `pnpm run build`.

Файлы: `index.html`, `src/App.vue`,
`src/components/GameBoard/GameBoard.vue`,
`src/components/GameBoard/internal/PendingTilePreview.vue`,
`src/components/GameTurnTracker.vue`,
`src/components/GamePrincessAndDragon.vue`,
`tests/browser/accessibility.spec.ts`.

### 4.5. Совместимость и устойчивость клиента — P1/P2

- **[Добавить] PWA/офлайн-оболочку** (по желанию): install, кэш статики,

- **[Проверить] Внешние шрифты Google** — приватность, CSP, скорость;

## 5. Тесты и CI

### 5.2. CI/CD — P1

- **[Проверить] Флейки:** `fileParallelism: false` задан в
  `vitest.integration.config.ts:19`, что детерминирует параллелизм тестов и
  снижает флейки от таймеров ИИ и ожиданий сокетов; бюджет времени CI
  фиксируется отдельно.

Инварианты этапа:

- Все GitHub Actions закреплены по SHA коммита, а не по тегам.
- `pnpm install --frozen-lockfile` гарантирует идентичные зависимости в CI,
  разработке и production; версия Node/pnpm фиксирована `engine-strict=true`.
- `pnpm audit` валит CI только на high/critical уязвимости.
- `pnpm run format:check` и `pnpm run lint` проходят для всего репозитория,
  включая `docs/`.
- Сервер считается готовым к трафику только после успешного `/ready` (200
  после захвата блокировки инстанса и загрузки партий, иначе 503).
- `fileParallelism: false` в vitest детерминирует параллелизм тестов.

Handoff:

- Для CodeQL и secret scanning в приватном репозитории организации нужны
  соответствующие права в настройках GitHub; для gitleaks в приватном
  репозитории может понадобиться `GITLEAKS_LICENSE`.
- Перед включением `pnpm audit` в блокирующий режим убедиться, что в текущих
  зависимостях нет уязвимостей уровня high/critical.
- Для деплоя в Render задать секреты `FIREBASE_API_KEY`,
  `FIREBASE_DATABASE_URL`, `FIREBASE_SERVICE_ACCOUNT`, `SESSION_SECRET`,
  `HEALTH_TOKEN`, `CLIENT_ORIGIN` в панели хостинга; применить
  `database.rules.json`. `RENDER_DEPLOY_HOOK_URL` — для вызова deploy-хука.
- Откат: Redeploy предыдущего коммита в Render или rollback через панель;
  состояние партий хранится в Firebase и переживает перезапуск сервера.
- Проверено: `pnpm run format:check`, `pnpm run lint`, `pnpm run type-check`,
  `pnpm test`, `pnpm run test:coverage`, `pnpm run build`,
  `pnpm --filter server run build`.

Файлы: `.github/workflows/ci.yml`, `.github/workflows/deploy.yml`,
`.github/dependabot.yml`, `vite.config.js`.

## 6. Юридические и продуктовые риски

### 6.1. Интеллектуальная собственность — P0 — [Проверить]

Название «Каркассон», правила игры, оформление тайлов и арты могут быть объектами авторского права или товарных знаков третьих лиц. Перед публичным релизом необходима юридическая проверка: право на использование названия, правил и графики в целевых юрисдикциях. Альтернатива — переименование проекта и собственная стилистика компонентов. Риск: требование прекратить использование, удаление контента, претензии после запуска.

Инварианты этапа:

- Публичный анонс не выходит до завершения проверки названия, правил и ассетов.
- В коде и клиенте нет заявлений об уникальности правил или названия, кроме отраженных в этом документе.

Handoff:

- Юрист или правообладатель даёт письменное разрешение или подтверждает отсутствие конфликта; иначе проект переименовывается и арты заменяются собственными.
- Результат проверки фиксируется здесь (статус меняется на [Сделано] с датой и ссылкой на акт/вывод).

### 6.2. Политика конфиденциальности и условия использования — P1 — [Добавить]

Отдельные страницы: какие данные хранятся (имя, цвет, игровое состояние, IP, технические идентификаторы, данные Firebase), зачем, сроки хранения, права пользователя (доступ, исправление, удаление, экспорт), контакт для запросов. Условия использования: правила сервиса, ответственность, прекращение доступа, изменение условий. Ссылки — в подвале клиента и при первом запуске.

### 6.3. Соблюдение GDPR/152-ФЗ — P1 — [Добавить]

В зависимости от аудитории (ЕС / Россия): основание обработки, согласие, право на удаление, экспорт данных, уведомление о нарушениях, ответственное лицо. Для 152-ФЗ — статус оператора персональных данных, уведомление в Роскомнадзор, место хранения данных. Требуется проверка юристом перед запуском для целевых стран.

### 6.4. Согласие на cookies/аналитику — P2 — [Добавить]

Если появится аналитика или хранение предпочтений в cookie, нужен баннер согласия и возможность отказа. Пока аналитики нет — пункт отложен до добавления аналитики.

### 6.5. Возрастной рейтинг и модерация публичных имён — P1 — [Добавить]

Возрастной рейтинг (PEGI/USK или локальный аналог) в зависимости от контента и платформ. Модерация имён игроков: уже есть автоматическая проверка на нецензурную лексику (п. 1.2), но нужно закрепить правила, алгоритм проверки, обжалование и блокировку повторных нарушителей. Публичные имена и чат (если появится) попадают под модерацию.

### 6.6. Канал поддержки и обработка жалоб — P1 — [Добавить]

Контакт для пользователей (email/форма), обработка жалоб на контент и поведение, сроки ответа, escalation. Связано с п. 1.5 (SECURITY.md — отдельный приватный канал для уязвимостей). Жалобы и ответы не логируются с персональными данными (см. инварианты п. 1.5).

### 6.7. Лицензии зависимостей и ассетов — P1 — [Проверить]

Проверить лицензии npm-зависимостей и сторонних ассетов (шрифты, иконки, изображения тайлов), собрать attribution. В производстве недопустимы проприетарные зависимости без лицензии или лицензии, запрещающие коммерческое использование. Результат — файл `THIRD_PARTY_NOTICES` или раздел в README.

Инварианты этапа:

- Юридические документы и проверки не заменяют код: серверные ограничения и правила Firebase действуют независимо.
- Персональные данные не хранятся дольше указанного в политике конфиденциальности срока.
- Согласие на обработку фиксируется явно там, где требует законодательство целевой аудитории.

Handoff:

- Политика конфиденциальности и условия использования готовятся юристом или по утверждённому шаблону и публикуются перед анонсом.
- GDPR/152-ФЗ проверяются для каждой целевой юрисдикции отдельно.
- Лицензии зависимостей проверяются при добавлении нового пакета; результат фиксируется в репозитории.
- Проверки: наличие документов, ссылки в клиенте, отсутствие запрещённых лицензий в зависимостях.

Файлы: `docs/`, `SECURITY.md`, `README.md`, `package.json`, `pnpm-lock.yaml` (для лицензий), клиентские страницы документов (по мере создания).

## 10. Проверки

Код приложения в рамках анализа не менялся, поэтому обязательные проверки не
запускались. Перед итоговым изменением использовать:

- `pnpm run check:all` — форматирование, типы, полный Vitest, ESLint, сборка;
- `pnpm --filter server run build` — отдельная компиляция сервера;
- `pnpm run test:coverage` — пороги покрытия;
- `pnpm run test:browser` — браузерный smoke (нужен Chromium);
- новые проверки из раздела 5.1 — после их добавления.

Документ является планом, а не утверждённым дизайном: перед реализацией
пунктов, меняющих протокол, сохранения или игровое поведение, нужно
согласовать решение и обновить `AGENTS.md`/тесты.
